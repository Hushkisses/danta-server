# DEV-017 — Snapshot / Important Flush

## Goal
Minimum restart recovery on top of DEV-016 PostgreSQL without blocking the Paper main thread during normal operation.

## Implemented
- DB snapshot namespace/key: `snapshot / active` in existing `danta_kv`.
- Snapshot schema v1 contains runtime elapsed/paused/speed and current minimal SeasonState.
- Startup: after PostgreSQL becomes READY, asynchronously load the latest snapshot and apply it on the Paper thread.
- Periodic snapshot every 5 real minutes (persistence housekeeping only; it does not advance RuntimeClock).
- Important-event API: `flushImportantAsync(reason)` for future capture/war/economy critical events.
- Shutdown: bounded 5-second final flush before DB executor closes.
- Manual DEV commands: `/danta snapshot save`, `/danta snapshot important <reason>`, `/danta snapshot load`.
- Local `runtime.properties` from DEV-011 remains a fallback if DB recovery fails.

## Recovery test
1. `/danta runtime set 7200`
2. `/danta snapshot important dev017-test`
3. Wait for `Important flush complete.`
4. `/danta runtime set 10`
5. Stop the server normally and start it again.
6. `/danta runtime status` should resume from approximately 02:00:00 plus only server-ON runtime after recovery, not from 00:00:10.

## Notes
RuntimeScheduler queue persistence is intentionally not included yet. DEV-017 provides the snapshot infrastructure; domain task persistence is attached when Army/Research/Construction tickets define stable task payloads.
