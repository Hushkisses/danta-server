# DEV-033 — Runtime movement scheduling and restart recovery

Status: COMPLETE — Windows build and Paper live-server verification passed

## Goal
Turn a validated one-leg MOVE order into a server-runtime reservation, keep it recoverable across restart, and complete arrival exactly once.

## Implemented
- `/danta army move` schedules `army.move.arrive` using the DEV-032 effective duration.
- Army status changes from `STATIONED` to `MOVING` when scheduling succeeds.
- Arrival updates the army location to the route destination, returns status to `STATIONED`, and removes the active order.
- Movement start and arrival trigger important asynchronous snapshot flushes.
- Snapshot schema v6 persists the active order route and `dueRuntimeMillis`.
- Codec remains backward-compatible with snapshot schemas v1-v5.
- Snapshot load reconstructs active ArmyOrder state and restores RuntimeScheduler tasks.
- If a restored deadline is already due at restored server runtime, the scheduler processes the arrival immediately.
- Server downtime itself does not advance RuntimeClock, so movement does not progress while the server is off.

## Scope boundary
- One adjacent edge only. Sequential multi-leg operation queues belong to DEV-034.
- Advance-stop conditions belong to DEV-035.
- No Paper main-thread DB I/O was introduced.

## Windows live-verification checklist
1. Stop Paper normally.
2. From the repository root run `git pull`.
3. Run `dev-server\\quick-deploy.bat`.
4. Start `dev-server\\start-dev.bat` and confirm `/danta db status` is 정상.
5. Load the dev map if needed.
6. Create a fresh army at `red_capital`.
7. Issue `/danta army move <army-id> red_farm`.
8. Immediately run `/danta army show <army-id>`: location must still be `red_capital`, status must be `이동 중`.
9. Run `/danta army order <army-id>`: the pending movement order must exist.
10. For a fast test, use `/danta runtime speed 100`. After about 1.1 real seconds for the 108-second e01 runtime trip, run army show again. Location must be `red_farm`, status `주둔 중`, and army order must report no current order.
11. Restart-recovery test: set runtime speed back to 1, create another fresh army at red_capital, start movement, wait for the important snapshot save log, then stop the server before arrival.
12. Leave the server off briefly. Start it again. The army must still be MOVING at red_capital; offline wall-clock time must not complete the trip.
13. Set runtime speed 100 and allow the remaining server-runtime duration to elapse. The army must arrive at red_farm exactly once and the active order must disappear.
14. Check the console for snapshot decode/restore errors or repeated arrival errors.
