# DEV-015 — Runtime Scheduler

## Goal
Run research/build/movement style jobs at an absolute server-runtime deadline without scanning all game systems every tick.

## Implementation
- `RuntimeScheduler` owns a `PriorityQueue<RuntimeScheduledTask>` ordered by `dueRuntimeMillis`.
- The Paper adapter pumps only the queue head once per server tick.
- Runtime pause automatically pauses task progress because deadlines are compared against `RuntimeClockService`.
- Runtime speed multipliers automatically accelerate scheduled jobs.
- Tasks use `taskType + payload` instead of storing `Runnable`, preparing them for persistence in later tickets.
- A task is removed before handler execution so repeated pumps cannot execute the same in-memory task twice.
- Handler failures are returned to the Paper adapter and logged.

## DEV command for manual validation
As an OP:

```text
/danta runtime schedule 10 hello
/danta runtime scheduler
```

The console should log the scheduled task after approximately 10 seconds of **runtime**, not wall-clock time.
Try `/danta runtime pause` and verify the task does not fire while paused. Try `speed 10` and verify a 10-runtime-second task completes in roughly 1 real second.

## Persistence boundary
DEV-015 is the in-memory scheduler. The task representation is intentionally persistence-friendly, but queue persistence/snapshot recovery is not added here; persistence infrastructure is handled by the later persistence/snapshot tickets and by each domain's durable orders.
