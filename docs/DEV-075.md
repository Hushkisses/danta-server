# DEV-075 — Prisoner / ransom / exchange / detention cap

Status: IMPLEMENTED — Windows automated verification pending

## Source basis
Design v0.3 states that a general may become a prisoner under defeat, blocked-retreat, isolation or pursuit conditions. Indefinite detention is forbidden. It assumes an initial maximum detention around 1.5–2 server-runtime hours, but explicitly lists the final maximum as still requiring final numeric confirmation. Before expiry, prisoners may be used for ransom, prisoner exchange and diplomatic negotiation. At expiry, automatic repatriation/escape determination must exist.
Execution plan v1.0 assigns DEV-075 to prisoner/ransom/exchange/detention cap.

## Implemented
- GeneralCaptivityState stores captor nation, capture runtime and detention deadline.
- GeneralState exposes captive state.
- GeneralCaptivityService handles capture, ransom-authorized release, exchange-authorized release and forced expiry release.
- Captor must be a different existing nation.
- A captive cannot be captured twice.
- A general must be detached from an army before capture, preventing an army from continuing to carry a captive commander.
- Detention is based on server runtime.
- No indefinite detention path exists once the caller/scheduler checks the deadline.

## Important boundary
The final detention maximum is NOT hard-coded to 1.5h or 2h because v0.3 explicitly marks the final value as unresolved. The service therefore requires a positive detention duration from configuration/orchestration.

Likewise, DEV-075 does not invent:
- ransom price/formula;
- who pays or receives ransom;
- diplomatic offer/acceptance UX;
- atomic two-prisoner exchange transaction;
- automatic-repatriation versus escape probability;
- capture probability from defeat/isolation/pursuit.

releaseForRansom/releaseForExchange are domain release transitions after the authoritative economy/diplomacy layer has accepted and, where applicable, atomically settled the agreement.

## Persistence/scheduler boundary
General persistence is still an open item. Captivity state must be persisted with generals when that snapshot is introduced. The runtime scheduler integration for automatic expiry must be wired at the same authoritative persistence boundary so restart cannot extend or lose detention.

## Automated tests
Tests cover capture, self/duplicate rejection, runtime deadline, forced expiry release and captor authorization for ransom/exchange release.
