# DEV-114 CombatAI Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add deterministic five-troop CombatAI foundations for infantry, spearmen, archers, cavalry, and magic troops, then expose a Paper validation boundary without implementing DEV-115 pathfinding or player magic.

**Architecture:** Extend the existing shared combat model with `MAGIC` and a support role, then add a Paper-independent `kr.danta.core.combat.ai` decision layer that maps minimal battlefield observations to high-level tactical actions. A small Paper adapter converts live/entity-facing state into core observations and exposes admin validation commands; actual waypoint navigation, concrete spells, and performance tuning remain deferred.

**Tech Stack:** Java 25, Gradle 9.7.1 multi-module build, JUnit 5, Paper 26.2 build 123.

**Spec:** `docs/superpowers/specs/2026-09-16-dev114-combat-ai-design.md`

## Global Constraints

- Core combat remains authoritative for troop concepts and strategic combat rules.
- Paper code handles Minecraft entity/runtime integration only.
- DEV-113 siege progression remains independent from individual entity AI.
- DEV-115 owns waypoint/path movement; DEV-114 must not implement a full pathfinder.
- DEV-116 owns 40-concurrent-AI benchmarking; DEV-114 only needs benchmark-friendly boundaries.
- Player-facing text must be Korean; internal enums/IDs may remain English.
- Player-cast magic is a separate later system; DEV-114 only adds `MAGIC` troop AI and a semantic `SUPPORT` action.
- Exact combat damage, spell lists, resource costs, cooldowns, mana-stone values, and final balance numbers are out of scope.

Also add tests for:
- infantry: `RETREAT` when survival threatened; otherwise `ENGAGE` at melee distance; otherwise `ADVANCE`, never `FLANK`/`PURSUE` from the tested frontline scenario
- archers: `RETREAT` when backline is threatened/hostile is too close; otherwise `ENGAGE` at safe range when protected
- cavalry: `FLANK` against exposed backline; `PURSUE` retreating hostile when no spear screen; avoids a spear screen by selecting `FLANK`/`HOLD` rather than direct `ENGAGE`
- magic: `RETREAT` when directly threatened; otherwise `SUPPORT` when an allied combat group exists; otherwise `HOLD`
- identical observation/profile calls return equal decisions

Use development decision thresholds only as named constants inside the controller; comments must state they are tactical implementation thresholds, not finalized balance.

- [ ] **Step 3: Implement minimal deterministic rules**

Use a single controller with small profile-specific private methods rather than five duplicate service classes. Priority order must make safety rules deterministic before offensive rules.

Required high-level ordering:

```text
all profiles: survival threat -> RETREAT
INFANTRY: melee range -> ENGAGE; otherwise -> ADVANCE
SPEARMEN: cavalry visible -> SCREEN(cavalry); threatened backline -> SCREEN; melee -> ENGAGE; otherwise -> ADVANCE
ARCHERS: unsafe close/backline threatened -> RETREAT; protected hostile in range -> ENGAGE; otherwise -> HOLD
CAVALRY: spear screen + no exposed alternate -> HOLD; exposed backline -> FLANK; retreating hostile -> PURSUE; otherwise -> FLANK
MAGIC: direct/backline threat -> RETREAT; allied group -> SUPPORT; otherwise -> HOLD
```

Do not add block coordinates, entity UUIDs, path nodes, spell IDs, cooldowns, or resource costs.
